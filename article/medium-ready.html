Is Docker Really Slower? Benchmarking Docker vs containerd vs CRI-O

I benchmarked the three container runtimes on the same machine, with the same image and the same runc binary underneath. The answer surprised me.

There is a popular belief that Docker is "fast" and the Kubernetes runtimes are "heavy", or the reverse: that Docker is bloated and containerd or CRI-O is the lean, fast choice. Both stories skip one detail that changes the whole question.

Docker does not run your containers. containerd does. When you type docker run, the Docker daemon hands the job to containerd, which hands it to a small shim process, which calls runc. CRI-O takes a different path to the same runc. So asking "is Docker faster than containerd?" is a bit like asking whether a car is faster than its own engine. (Docker is that teammate who presents the group project that containerd quietly built.)

The better question is: how much does each layer cost, and when is that cost worth paying? That's what I measured.

The stack: three front doors, one engine room

All three runtimes end at the same place: runc, the reference OCI runtime that actually creates namespaces and cgroups and starts your process. Kubernetes' own docs note that runc is the default low-level runtime for both containerd and CRI-O. What differs is how many layers sit in front of it.

[ IMAGE 01-stack-diagram.png ]

Docker's path in one sentence: you ask dockerd, who asks containerd, who asks a shim, who finally asks runc to do the actual work. Very enterprise. Three layers of management for one sleep command.

[ IMAGE 02: your meme ]
  • dockerd is the Docker Engine. It owns the developer experience: the REST API, docker build (BuildKit), networks, volumes, Compose. Since Docker Engine 29, new installs also use containerd's image store by default, so images and execution both live in containerd now.
  • containerd is a general-purpose container daemon (CNCF graduated). It pulls images, manages snapshots, and supervises containers. It includes a CRI plugin, so the Kubernetes kubelet can talk to it directly.
  • The shim (containerd-shim-runc-v2) is a small Go process that sits between containerd and each container. It keeps the container alive if containerd restarts.
  • CRI-O is a daemon built for one job: implementing the Kubernetes Container Runtime Interface (CRI). Its releases track Kubernetes minor versions (CRI-O 1.34 for Kubernetes 1.34). It is the runtime behind Red Hat OpenShift.
  • conmon is CRI-O's per-container monitor. It does the same job as containerd's shim, but it's written in C.

Kubernetes removed its built-in Docker support (the dockershim) in v1.24. Since then, a Kubernetes node normally runs containerd or CRI-O directly, and Docker lives on developer laptops and CI machines.

The benchmark setup

Everything ran on one machine, with all three daemons running side by side and the same low-level runtime:

  • Machine: 2 vCPU, 8 GB RAM cloud VM, Ubuntu 24.04, kernel 6.18, cgroup v1
  • Docker Engine: 29.9.3 (containerd image store, overlayfs snapshotter)
  • containerd: 2.4.2 (also the containerd that Docker uses)
  • CRI-O: 1.34.14 with conmon 2.1.10, driven by crictl 1.34
  • runc: 1.5.2, shared by all three
  • Image: a 3 MB busybox image built FROM scratch, loaded into all three image stores

What I measured. Start latency: the time from invoking the CLI until it returns with the container running (a detached sleep). The image is already local, so no pulls. Cleanup happens outside the timed region. Each variant ran 50 times after 5 warm-up runs, and the order of variants was shuffled every round so background noise hits them all equally. I report the median and the 95th percentile (p95), not the mean.

The six variants:

  1. runc run -d: the raw runtime with no daemon at all. This is the floor.
  2. ctr run -d: containerd's own debugging CLI.
  3. docker run -d --network none: Docker without networking, to isolate the engine cost.
  4. docker run -d: Docker with its default bridge network.
  5. crictl create + crictl start in an existing pod: how the kubelet starts a container in CRI-O.
  6. crictl runp + create + start: a brand-new Kubernetes-style pod (a sandbox with a pause container, then the app container).

I also measured memory: each daemon's PSS (proportional set size, which splits shared pages fairly) when idle, and again with 20 idle containers running.

Result 1: start latency

containerd was fastest (100 ms median), CRI-O came second (129 ms), and Docker came last (153 ms, or 167 ms with its default bridge network). The raw runc floor was 27 ms.

Yes, the most famous container tool on the planet finished last. In its defense, it showed up carrying snacks: image builds, Compose, networks and volumes. containerd showed up with a gRPC socket and a dream.

In the chart, the dot is the median and the line runs to the p95:

[ IMAGE 03-latency.png ]

A few things stand out:

  • Docker is not the fast one. It adds about 50 ms over plain containerd, and its default bridge network adds about 15 ms more (creating a veth pair and wiring it to docker0).
  • The gaps are small in absolute terms. Among the three daemons, the slowest single-container path is about 1.7× the fastest, and every one of them is far below what a human notices at a terminal.
  • CRI-O's "new pod" number (243 ms) is not a like-for-like comparison. It starts two containers: the pod's pause sandbox (a process whose entire job is to do nothing, professionally, forever) and your app. That's the real cost of a Kubernetes pod start, and it's the number to compare if you care about pod churn.
  • Most of the cost is not runc. runc alone took 27 ms; everything above that is daemons, gRPC calls, shims, and CLI startup.

Result 2: memory

With 20 containers running, CRI-O used 87 MB in total, containerd 140 MB, and Docker 240 MB. The ranking flips depending on what you count.

When idle, containerd is the lightest daemon at 51 MB, then CRI-O at 79 MB. Docker needs both dockerd (101 MB) and containerd, so about 152 MB before you start anything.

[ IMAGE 04-memory.png ]

Per container, the picture changes. Each containerd shim is a Go process using about 4.2 MB. Each CRI-O conmon is a C process using about 0.4 MB, roughly ten times less. Turns out you don't need a garbage collector to babysit a process that mostly sleeps. With 20 containers, that's 84–86 MB of shims for Docker and containerd against 8 MB of conmon for CRI-O.

One caveat that matters in production: when containerd runs Kubernetes pods through its CRI plugin, the containers of one pod share a single shim. The per-container cost I measured (one container per shim, as docker run and ctr run do) is closer to a per-pod cost on a Kubernetes node.

Where Docker's extra 50 ms goes

About 20 ms of Docker's extra time is its heavier docker CLI, and about 30 ms is dockerd's work on top of containerd. I split it by calling the Docker Engine API directly over its Unix socket, with no CLI process, and by timing each CLI binary doing nothing.

[ IMAGE 05-where-the-ms-go.png ]

The measurements behind the split (medians):

  • docker run -d --network none through the CLI: 153 ms
  • The same container through the raw Engine API (create + start): 122 ms
  • ctr run -d through the CLI: 100 ms
  • The docker CLI starting up with no daemon call (docker context show): 17 ms
  • The crictl CLI starting up (crictl --help): 14 ms
  • The ctr CLI starting up (ctr --help): 10 ms

Roughly:

  • CLI cost (~30 ms, about 20 ms more than ctr's): the docker binary is bigger and slower to start than ctr, and docker run makes several API round trips (a version ping, create, then start).
  • dockerd's own work (~30 ms): Docker's API at 122 ms against containerd's ~90 ms (100 ms minus its CLI startup). That pays for container config, the network sandbox, logging setup, and an extra gRPC hop.
  • CRI-O sits in between: its 129 ms includes two separate crictl processes (create, then start), about 27 ms of CLI startup. The kubelet talks gRPC directly, so in a real cluster that part disappears.

So the runtimes themselves are within about 30 ms of each other. Nearly half of Docker's famous "slowness" is the docker binary getting out of bed. Honestly, relatable. In a tight loop, the CLI you use matters about as much as the daemon behind it.

Update: I reran it on Apple Silicon, and crun stole the show

The first run left two big gaps: ARM and cgroup v2. So I reran the whole suite on an Ubuntu 26.04 VM on an Apple Silicon Mac: 4 vCPU, 6 GB RAM, cgroup v2, Docker 29.10.0, containerd 2.4.2, CRI-O 1.37.4 and runc 1.5.3, through the same kit you can run yourself (link below).

This time I added a seventh variant: CRI-O as it ships. Since v1.31, CRI-O uses crun by default, a low-level runtime written in C, instead of runc (written in Go). For the main comparison I still force CRI-O onto the same runc as everyone else. The crun row shows what you get out of the box.

[ IMAGE 07-arm-latency.png ]
  • CRI-O with crun: 31 ms. The fastest of all, ahead of containerd (37 ms).
  • CRI-O with runc: 48 ms. Same CRI-O, same pod; the only change is the low-level runtime, and it costs 16 ms.
  • Docker: 63 ms (80 ms with the bridge network). Still last.
  • A brand-new CRI-O pod: 80 ms, the same as a single docker run with networking.
  • runc alone: 13 ms.

Here's the surprise: swapping runc for crun saved more time (16 ms) than dockerd costs (14 ms). We spend a lot of energy arguing about which daemon to run, while the small binary at the bottom of the stack moves the needle just as much. A short smoke run before the full one gave the same order (crun 34 ms, containerd 35 ms, CRI-O with runc 44 ms), so it's not a one-off. It is one machine, though.

The rest of the story holds, just faster. Everything ran about 2–3× quicker than on the small cloud VM, and the ranking of the three daemons didn't change. Docker's extra cost over containerd shrank to about 25 ms, roughly half dockerd (14 ms) and half its CLI (about 11 ms more than ctr):

[ IMAGE 08-arm-where-the-ms-go.png ]

Memory went the same way, only more so. With 20 containers: Docker 279 MB, containerd 180 MB, CRI-O 72 MB. A containerd shim still costs about 3.8 MB per container; a CRI-O conmon was down to about 0.1 MB.

[ IMAGE 09-arm-memory.png ]

One thing I couldn't confirm: on this machine, running all three daemons side by side versus one at a time moved the medians by up to 15 ms in both directions, which is noise, not a pattern. So for this run I'd trust the ranking, not the isolation result.

So which one should you use?

Pick by job, not by milliseconds. A 30–50 ms difference per container start rarely decides anything. What each tool is built for does. Picking a runtime to save 50 ms is like buying a sports car to get through red lights faster.

[ IMAGE 06-which-to-use.png ]

Use Docker on your laptop, in CI, and on single servers. You get image builds, Compose, a friendly CLI and the biggest ecosystem. Its overhead buys you features you actually use there.

Use containerd as the runtime of a Kubernetes node (it's the default on most managed clusters and in k3s and kind), or when you build your own platform and want a stable, embeddable daemon. Pair it with nerdctl if you want a Docker-like CLI without dockerd.

Use CRI-O when the node exists only to run Kubernetes and you want the smallest surface: nothing that Kubernetes doesn't need, versions locked to your Kubernetes release, and the lowest per-container memory. It's the natural choice on OpenShift and in Red Hat-based stacks. And keep its default crun: on my ARM run it was the fastest way to start a container.

Don't switch runtimes for speed alone. If pod start time hurts, look first at image size and pull time, CNI setup, and init containers. In my test, a new pod's sandbox cost more than the whole difference between the three daemons.

In short: caveats and how to run it yourself

Two machines now: a small x86 cloud VM (2 vCPUs, cgroup v1) and an Apple Silicon VM (4 vCPUs, cgroup v2). The ranking held on both; the milliseconds didn't, so trust the ranking more than the exact numbers. Benchmarks are like horoscopes: oddly specific, and not about your production cluster.

  • Not measured: image pulls, real workloads, concurrent starts, bare metal.
  • CLI startup is included in the timings; the kubelet never pays it.
  • CRI-O 1.34 built from source on the first machine, the packaged CRI-O 1.37 on the second; Docker shares containerd, so its memory includes containerd's.

The kit is on GitHub at github.com/yobahadda/bench_Crio_ContainerD. On a fresh Ubuntu 24.04+ VM, one Ansible playbook installs all three runtimes, and the whole suite runs in 3 to 10 minutes depending on the machine:

git clone https://github.com/yobahadda/bench_Crio_ContainerD.git
cd bench_Crio_ContainerD
make provision && make doctor && make bench
